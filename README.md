The Helm chart that installs [AIsolate](https://github.com/reportix/aisolate) on Kubernetes: governed model endpoints over the
organisation's own databases. It installs the `Space` and `Airlock` custom resource definitions (`aisolate.dev/v1`), the controller
that turns them into airlock pods and tool server pods, and the namespace's default-deny NetworkPolicies; `headless=false` adds the
AIsolate UI with its backend and PostgreSQL, and `platform.chat.enabled`, `platform.keycloak.enabled` and
`platform.egress.proxy.domains` the sample chat, a Keycloak of the chart's own and a CONNECT-only egress proxy.
What the cluster, the identity provider, the databases and the model server must provide is AIsolate's documentation:
[install](https://github.com/reportix/aisolate/blob/main/docs/install.md),
[release](https://github.com/reportix/aisolate/blob/main/docs/release.md) and
[concepts](https://github.com/reportix/aisolate/blob/main/docs/concepts.md).

## Install

Create the namespace and label it for the restricted Pod Security Standard first: Helm does not manage the release
namespace.

```bash
kubectl create namespace aisolate
kubectl label namespace aisolate pod-security.kubernetes.io/enforce=restricted
helm repo add aisolate https://sonatype.reportix.com/repository/helm-public
helm install aisolate aisolate/aisolate --version <version> -n aisolate -f values.yaml
```

Every tag `<version>` publishes the package; from a checkout, `helm install aisolate chart -n aisolate -f values.yaml`. Helm
installs `chart/crds` (generated by AIsolate's controller, copied here by `scripts/pin-release.sh`, never edited by hand) on the first install only:
run `kubectl apply --server-side --force-conflicts -f chart/crds` before every `helm upgrade`.

Then apply a `Space` and its `Airlock`s: the export is one file for `kubectl apply -f`, Argo CD or Flux, or `aisolate deploy` with
the UI (a headless install runs airlocks without code only). Create the Secrets its `secretRef`s name first, with the keys
`username` and `password`. Once a `Space` exists, `helm test aisolate -n aisolate` checks from a pod that the release answers
through the ingress controller and that its discovery pods, and the Services in `test.toolServers`, are unreachable.

## Values you will set

`chart/examples/example-values.yaml` is a production starting point; [chart/README.md](chart/README.md) lists every parameter.

- **Images.** A published chart pulls every AIsolate image from `docker-public.sonatype.reportix.com`, pinned by tag to its
  appVersion; set `digest` on an image to pin it harder (a digest wins over the tag). The UI's and the chat's have no default
  registry, since they carry their deployment's URLs from their build: build each, then set its registry and its tag. The
  airlock and the tool server come twice, Java and Python (`platform.airlock`, `platform.toolServer`,
  `platform.airlockPython`, `platform.toolServerPython`): the controller runs an airlock on the pair of its code's language.
  `allowTags: false` makes every AIsolate image need its digest. For a private registry, `global.imageRegistry` reaches every image, the controller's pods
  included, and `global.imagePullSecrets` the chart's own pods; the airlock and tool server pods run as the namespace's `default`
  ServiceAccount, so give it the Secret:
  `kubectl patch serviceaccount default -n aisolate -p '{"imagePullSecrets":[{"name":"<secret>"}]}'`.
  `<image>.pullSecrets` was removed in 0.2.0: put the names in `global.imagePullSecrets`, same effect.
- **The identity provider.** `platform.identity` for the users', and `platform.identity.operators` when the dashboard and the CLI
  use another; a separate operators' host needs its own `egress` peer, or the backend cannot reach it.
- **The cluster's peers**, under `platform.egress`: the DNS, the ingress controller, the API server (`apiServer.cidr`: without
  it the controller and the backend may reach any address on its ports) and, in `hosts`, the hosts of every LLM and data source
  defined for all of AIsolate or by a space or an airlock, each with its NetworkPolicy peer: an airlock that resolves a host
  neither mapped nor proxied is `Invalid`. `proxy.domains` names the hostnames the egress proxy may reach; a host on it needs no
  `hosts` entry.
- **The Ingresses**, under `platform.ingress`: `host`, `publicUrl`, `className`, `tls` (on ingress-nginx the release host's certificate also covers
  the Ingresses the controller renders) and `annotations` (cert-manager). With the UI also `platform.frontend.host` and `platform.backend.host`; its image carries the backend's URL and the operators' provider
  from its build (`NEXT_PUBLIC_AISOLATE_URL`, `NEXT_PUBLIC_OIDC_AUTHORITY`), so build it for those hosts.
- **A node pool**, `platform.scheduling`: node labels and tolerations for every pod of the release, the controller's included.
- **Keys, where the chart is rendered without cluster access** (Argo CD, `helm template`): set
  `persistence.postgres.existingSecret`, `platform.audit.existingSecret` and `platform.credentials.existingSecret` (and
  `platform.keycloak.existingSecret`). The chart cannot keep a generated key there, and every sync would make a new one.

## End-to-end test

`tests/e2e/run.sh` installs the chart from this tree on a new kind cluster with `allowTags`, the chart's Keycloak and a
stub model server, deploys one airlock without code (the `company-hr` template's documents), runs `helm test` and asks
the airlock a question through the ingress as a Keycloak user, then deletes the cluster (`--keep` leaves it). It needs
Docker 28 or newer (Docker Desktop on a laptop), kind, helm, kubectl 1.31 or newer, curl and jq, and the images
`aisolate/controller:local` and `aisolate/airlock:local` built in the app repository:
`./gradlew :apps:controller:bootJar :apps:airlock:bootJar`, then `docker build -t aisolate/<app>:local apps/<app>`.
`--images <prefix>:<tag>` names others. `--context` runs on an existing cluster and changes it: it applies the CRDs,
installs ingress-nginx when absent and leaves it, labels the namespace restricted, upgrades a release `aisolate` there
and loads no images; give it a namespace you own on a cluster that can pull them. CI's manual `test_deploy` job runs it
with the app's snapshot images from the internal registry: `AISOLATE_IMAGE_TAG`, a `<version>-<sha10>` of its `main`.

## Releasing

The chart follows the fleet's deploy/release flow (the `release@1` component of `reportix/ci-templates`):

- **Every merge to `aisolate/aisolate` `main`** publishes its images to `docker-internal` as `<version>-<sha10>` and its
  `release-deploy` job writes those tags into `chart/values.yaml` on this repository's bot branch `next`, merged to `main`
  by an auto-merged merge request. `main` therefore always installs the app's newest merge. Never edit the seven image
  pins by hand.
- **A release:**
  1. Tag the release in the app repository (`aisolate/aisolate`), bare semver; its pipeline publishes the images to
     `docker-public.sonatype.reportix.com`.
  2. Play `chart-prepare-release` on `main`'s newest pipeline with `CHART_RELEASE_VERSION` (strictly above `main`'s
     `version`): it rewrites the image pins to `docker-public…:<version>`, checks every one exists, bumps `version` and
     opens the merge request `release/<version>`.
  3. On that branch run `scripts/sync-app.sh <appVersion>` (`--dry-run` first): it writes `appVersion` and the CRDs of
     the app's tag. Then `tests/chart/regenerate.sh`, and push.
  4. Merge, then tag `main` with the chart's `version`: CI refuses a tag whose values still name an image the public
     channel lacks (`chart_image_gate`) and publishes the chart to the public Helm repository.
